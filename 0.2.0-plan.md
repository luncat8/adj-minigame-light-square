# 0.2.0 targets, difficulty, generation

Base: 15x15 board, four rings, quarter/shift modes, mask trace, settings panel.

## target model

A puzzle has `b.groups`, an array of target groups. A group is:

- `cells`: array of `{ idx, mask }`. `idx` is a border cell index. `mask` is 1..7 for an exact color, 0 for any color.
- `need`: number of cells that must be good, 1..cells.length.
- `exact`: boolean. True means each listed cell must match its mask. False means any light counts.

A cell is good when:

- exact: `grid[idx].light === mask`.
- any: `grid[idx].light > 0`.

A group is satisfied when at least `need` of its cells are good. The puzzle is solved when every group is satisfied.

Groups are disjoint; a border cell belongs to at most one group. A group with `need < cells.length` is a choice task: the player may satisfy any subset of the required size.

A beam separates into at most three color channels, so a trace lights at most three exit cells plus the entry cell: four lit border cells. Group count and size stay inside that budget.

## why choice and any-color are easier

- Any-color removes color routing: the beam only has to reach the cell, not produce a specific RGB mix.
- `need < cells.length` gives the player a choice of which cells to satisfy; hard cells can be ignored.
- Fewer required cells and fewer groups reduce the number of independent constraints.
- Fewer scrambled rings and shallower scramble reduce the number of moves.
- Exact all-cells is hardest: every listed cell needs a precise mask, and one wrong beam fails the group.

## difficulty

`Game.settings.difficulty` is 0..1, default 0.5. It selects a tier float `t = difficulty * 4`; adjacent tiers blend their ranges. Generation samples ring count, scramble depth, group count, group size, need, and exactness inside the blended ranges.

`Generate.DIFFICULTY` is the tier table:

```
tier  max   rings  depth  groups  size  need  exact
0     0.20  1      1      1       1     1     no
1     0.40  1-2    1-2    1       2-3   2     no
2     0.60  2-3    2      1-2     2-3   2     yes
3     0.80  3      2-3    2       2     2     yes
4     1.01  4      max    2       2     2     yes
```

`rings` counts distinct rings from 0..2; tier 4 includes ring 3 (the 1x1 flip). `depth` is a cap per ring; `max` means `floor(period / 2)`, the shortest nonzero rotation. `need` is capped at `size`. `exact` is per puzzle; near a tier boundary the blended value is a probability. Active rings are drawn from the rings the laser column crosses, so a scramble always affects the beam.

`Board.difficultyScore(b)` returns 0..1:

`0.4 * depthScore + 0.3 * strictScore + 0.2 * colorScore + 0.1 * groupScore`

- `depthScore` = average over rings of `min(turns[r], period[r] - turns[r]) / floor(period[r] / 2)`, with unscrambled rings at 0.
- `strictScore` = average `need / cells.length` over groups.
- `colorScore` = exact groups / groups.
- `groupScore` = `(groups.length - 1) / 2`.

The score is stored on the board and shown in the status line. It is the calibration metric, not a hard acceptance gate. Generation retries only on invalid puzzles.

## generation

`Generate.make(rng, settings, trace)`:

1. Create the board, fill glass, force the center cell to be a mirror.
2. Choose solved ring positions in the active mode; include the 1x1 flip when the profile says so.
3. Choose a laser column inside the 7x7 glass. Sample up to 8 columns and keep one with enough lit border cells for the requested groups; tie-break randomly.
4. Trace the solved state and collect lit border cells with their masks.
5. Scramble each active ring by a random `1..floor(period/2)` inputs in the active mode, with a random direction. Active rings are chosen from the rings the laser column crosses. Normalize the ring counters modulo their periods and store `startTurns` normalized.
6. Trace the start state.
7. Build groups from the collected cells:
	- any-color groups draw cells with `light > 0`; mask 0.
	- exact groups draw cells with a required mask; prefer cells that are not good at the start state.
	- sample without replacement across groups.
	- `groups * size` must fit the lit cells; a profile that does not fit is rejected and resampled.
8. Reject and retry if:
	- the start is solved;
	- any group is already satisfied at the start (`goodStart >= need`);
	- a laser-only move solves the puzzle with the start rings;
	- a group has fewer than `need` cells that are good in the witness state (assert; cannot happen by construction).
9. Store `solutionTurns`, `startTurns`, `solutionLaser`, `laserWidth = 1`, `difficulty`, `difficultyScore`.

The witness state is `solutionTurns` plus `solutionLaser`. `Board.isSolved` on the witness is asserted before returning. If 24 attempts fail, return a deterministic easy profile puzzle (one any-color group, one ring scrambled once) that passes the same assertions rather than an invalid board.

## laser width

Generated puzzles use laser width 1. The width control is deferred and is not exposed in the panel; the 1-3 width keys are removed from input. `Game.setWidth` stays available for the deferred setting but no UI calls it. Width is an optical property, not a visual-only setting: it lights every column in `[laserStart, laserStart + width)`. If it returns, it becomes part of puzzle state, difficulty, and the solver, and generation must reject width-only solutions. The README controls line drops `1-3 width`.

## solvability

Every generated puzzle has a witness. `engine_smoke` generates 200 seeds per mode and per slider value 0, 0.5, 1 and asserts:

- the witness solves all groups;
- the start is not solved;
- no laser-only move solves the start;
- every group has `goodStart < need`.

## panel

The panel gains a range input `#difficulty` (0..100) and a label `#difficultyLabel` (`Easy`, `Casual`, `Medium`, `Hard`, `Expert`). The slider calls `Game.setDifficulty(value)`, which updates `Game.settings.difficulty` and `UI.sync`; it does not regenerate. `New puzzle` uses the current slider value. The status line shows `d 0.50`.

## render and status

`Renderer.drawTargets` draws one diamond per target cell. Exact cells use the required color; any-color cells use white. A small group number (`1`..`3`) is drawn in the top-left corner of each target cell. 0.3.0 adds per-cell status and hint overlays.

## experiments

`experiments/difficulty.js`:

- for each mode and slider value 0, 0.25, 0.5, 0.75, 1, generate 100 puzzles (`node experiments/difficulty.js <mode> <sample>`);
- record `score_avg`, `score_p10`, `score_p90`, `par_avg`, `par_p90`, `gen_ms_avg`, `reject_avg`, `fallback_avg`;
- write `logs/difficulty-<mode>.log` in `key=value` lines.

`par` is the minimum number of player inputs to solve, measured by BFS over ring turns and laser column (quarter mode: 4^3 * 2 * 15 states; shift mode: 24*16*8*2*15 states). BFS is an experiment, not runtime; states are capped at 20000 per puzzle.

A ~15-line `experiments/compare.js` diffs two logs by key and flags `|delta| > 5%`.

Manual pass:

- slider at 0 and 1; generate several puzzles; check target count, exactness, and mode.
- switch mode; generate; check the profile uses the mode's period.
- solve one puzzle by hand; status shows all groups and `SOLVED`.
