# 0.8 · Continuous difficulty dial

Replace the three-step `band` slider with a continuous difficulty dial (0..1) that *means*
something: generation blends its parameters by the dial, then **measures** the resulting
puzzle and selects the candidate whose measured difficulty best matches the dial. Keep the
current contract scoring, replay-verified witness, and preset fallback untouched — the dial
only changes how generation parameters are chosen and how a puzzle is picked. Two earlier
prototypes point the same way (`archive/0.8.0-comparison-report.md`, `archive/0.7.0-comparison-report.md`):
f286079 shows the forward blend + `par()` measurement, bc2bdf2 shows `sampleWinRate`
candidate selection with a separate scoring RNG stream. This plan reuses both shapes.

## 1 · Dial → generation profile

`generate.js` owns a `profile(rng, difficulty)` that returns continuous parameters by
blending anchor tiers, the f286079 `Generate.profile` shape adapted to the contract model:

- `quotaFrac`: 0.5 → 1.0 (band 0 was ⌈h/2⌉, bands 1/2 were h).
- `exactProb`: 0 → 1, ramping in only above the midpoint so easy puzzles stay "any color"
  and the top of the dial forces exact colors (strict contract).
- `scrambleDepth`: scales `BAND_DEPTH` linearly, ~3 at 0 → ~14 at 1.
- `ringEngage`: count of rings allowed to differ, 1 → 4.
- `emitterRange`: widens the usable emitter column span with difficulty.

Anchors sit at 0 / 0.33 / 0.66 / 1.0; `profile` interpolates between the two bracketing
anchors by `f = difficulty * 3`. Clamp so quota never exceeds the witness hits (0.4 rule:
never request a quota beyond witness hits) and `exactProb` only produces a strict contract
when every hit carries a mask.

## 2 · Measured difficulty

For each generated candidate compute a single difficulty number `d`:

- **Primary — `par()` BFS** (f286079 `par()`, generalized from "groups satisfied" to the
  contract win predicate). State = `(emitter, ringTurns[0..3])` with each turn modulo its
  period. Quarter-mode periods are 4/4/4/2 × 13 emitter columns = 1664 states (trivial);
  single-mode periods are 24/16/8/2 × 13 ≈ 80k. Neighbors are ±1 shift per ring and ±1
  emitter (bounds-checked). Solved when `evaluateContract(contract, traceRecv).won`.
  Mutate the board in place along BFS edges (apply move / inverse) so each state is traced
  once. `d = BFS depth` (minimum moves to win).
- **Fallback — win-rate sampling** (bc2bdf2 `sampleWinRate`) when the product of ring
  periods × emitter columns exceeds a state cap (mirror f286079's `par(b, 20000)` cap, use
  the same 20k). Run W random walks of up to S steps (64 × 20) from the start pose; `d =
  fraction of walks that reach a won pose`. Stochastic but adequate for selection.

`par()` lives in `generate.js` (it owns solvable generation and difficulty); it uses the
existing `traceLight` / `evaluateContract` and adds only a per-candidate BFS buffer
allocated once and reused.

## 3 · Candidate selection

`generate(rng, mode, corner, difficulty, opts)` samples `K` replay-verified candidates
(`K = 8`, bc2bdf2's best-of-8) through the existing witness → contract → scramble →
replay-verify pipeline, measures `d` for each, and returns the candidate whose `d` is
closest to the dial's target `T(difficulty)`. The target `T` maps the dial to a difficulty
band (par or win-rate) so the slider is monotonic by construction. If fewer than `K`
candidates verify within `maxAttempts`, pick the best of what verified; if none verify,
return the preset as today.

**Separate scoring RNG stream:** candidate sampling and `d` measurement draw from
`makeRng(seed ^ 0x9e3779b9)`, never from the generation `rng`. This is the bc2bdf2 lesson
recorded in `findings-pitfalls-skills.md` — sampling must not perturb generation, or the
same seed no longer reproduces the same puzzle.

## 4 · UI and readout

`index.html`: replace `<input type="range" id="band" min="0" max="2" step="1">` with
`<input type="range" id="difficulty" min="0" max="100" step="1" value="50">` plus a live
`<span id="difficulty-label">`. `game.js` reads `difficulty/100`, passes it to `generate`,
and renders the label from the measured `d` of the chosen puzzle (e.g. `par 4` or
`winRate 0.62`) instead of the static band text. Changing the dial alone never regenerates
(current rule: rules and difficulty apply only on Generate).

## 5 · Measurement harness (0.4 plan's open task)

Port f286079's `experiments/difficulty.js` + `experiments/compare.js` to the current model:

- `difficulty.js`: for each `mode` (quarter, single) × `corner` (on/off) × `difficulty ∈
  {0, .25, .5, .75, 1}`, generate `N` puzzles and log, one line per metric, machine format:
  `mode= quarter difficulty=0.50 sample=200 par_avg=4.10 par_p90=7.00 par_cap=12
  winrate_avg=0.41 gen_ms_avg=1.20 reject_avg=0.30 fallback_avg=0.000`.
- `compare.js`: diff two logs by key, flag `|Δ| > 5%`, print a one-line conclusion.

Use the sweep to **calibrate** the dial→`T` mapping: confirm `par_avg` (or `winrate_avg`)
rises monotonically with the dial and that adjacent dial values are statistically distinct
(`compare.js` flags the gaps). Put the calibration conclusion in `findings`, raw logs in
`logs/`.

## Acceptance

- Dial 0..1 replaces band 0..2; sliding it alone does not regenerate; Generate still applies
  it.
- Measured difficulty rises monotonically across the dial in both modes (sweep), adjacent
  values distinguishable (`compare.js` `|Δ| > 5%`).
- Selected puzzle's `d` tracks the dial target within tolerance; recorded solution length
  (or par) grows with the dial.
- Zero invalid witnesses / already-won starts; preset fallback still triggers when bounded
  out; `gen_ms_avg` at dial 0.5 not regressed > 5% versus the band baseline.
- Manual: slide easy→hard, watch the `d` label rise and play feel harder (not just longer);
  preview and rim items behave as in 0.5/0.6.

## Build order

1. `generate.js`: `profile(rng, difficulty)` + `par()` BFS with state cap; unit hooks via
   `generate_fixtures.js` (par determinism, quarter = 1664-state exactness).
2. `generate.js`: best-of-K selection + separate scoring RNG stream (`seed ^ 0x9e3779b9`);
   win-rate fallback when capped.
3. `index.html` + `game.js`: continuous `difficulty` range, label from measured `d`.
4. `experiments/difficulty.js` + `compare.js`: sweep + calibration; record conclusion in
   `findings`.
